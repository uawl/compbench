# v1 코드 생성기 비교

> 이 문서의 측정값은 버전 분리 전 하네스에서 얻은 기록이다. 재현 명령은 분리된 v1의 정수 AST·2인자 ABI를 사용한다. 당시 측정 루프에는 arena 초기화가 포함되어 있었으므로 새 측정값과 혼합하지 않는다.

Gemini의 성능 향상에는 벡터화와 스칼라 로직 최적화가 모두 기여한다. 배열 합계·최댓값·조건부 합계는 벡터 경로의 영향이 크고, 상호 재귀와 비꼬리 재귀는 실제 계산 구조도 바꾼다. 보조 함수 문제에는 실행 가능한 벡터 경로가 생성되지 않았으며 스칼라 언롤이 주요 차이다.

## 비교 방법

`res/v1` 원본은 수정하지 않았다. `build/analysis/v1`에 복사본을 만들고 최적화 호출만 비활성화했다. 같은 v1 문제 8개, 시드 3235782694, 같은 스칼라 베이스라인과 현재 측정 하네스를 사용했다. 각 변형은 원래 정확성 검사를 모두 통과했다. 측정은 순차 실행했으며 기본 하네스의 7회 중앙값을 사용했다. 아래 수치는 이번 실행 결과이며 측정 잡음과 최적화 사이의 상호작용이 있다.

| 구현/변형 | 베이스라인 대비 기하평균 |
| --- | ---: |
| Astra 원본 | 2.64배 |
| Gemini 원본 | 9.83배 |
| Gemini: 벡터 경로 끔, 스칼라 언롤 유지 | 4.56배 |
| Gemini: 벡터 경로와 스칼라 언롤 끔 | 3.32배 |
| 위 스칼라 버전에서 비꼬리 재귀 변환도 끔 | 3.06배 |
| Gemini 원본에서 상호 재귀 인라이닝만 끔 | 8.80배 |

벡터 경로 제거는 `emit_avx2_fastpath()` 호출을 건너뛰고 기존 스칼라 경로를 사용한다. 이 스칼라 경로는 4회 언롤을 시도한다. 언롤 제거는 `try_emit_unrolled_scalar_loop()`도 건너뛴다. 비꼬리 재귀 변환 제거는 `convert_linear_rec_to_loop()`와 `detect_right_spine_recursion()`을 모두 비활성화한다. 상호 재귀 인라이닝 제거는 인라이닝 패스의 `allow_mutual`만 0으로 지정한다. 공통 진입 코드의 `vzeroupper`는 그대로이므로 벡터 경로 제거가 AVX 명령어 전체 제거를 뜻하지는 않는다.

### 배열 합계와 최댓값

Astra는 스칼라 반복문을 생성하고 원소별 종료 조건·배열 범위를 검사한다. 합계에서는 다음 인덱스를 스택에 임시 저장하고 다시 읽는다.

Gemini 벡터 경로는 네 원소씩 `vmovdqu`로 읽으며, 단일 누산기 문제에서는 벡터 두 개로 여덟 원소를 처리한다. 합계의 두 벡터 누산기는 마지막에 합친다. 처리 가능한 범위를 루프 전에 계산해 원소별 범위 검사를 제거한다. unsigned 최댓값은 최상위 비트를 XOR한 뒤 signed 벡터 비교로 선택한다.

따라서 원본 Gemini의 합계가 Astra보다 약 15.7배 빠른 것을 벡터 폭 4배만으로 설명할 수 없다. 벡터 경로에는 언롤, 누산기 분리와 검사 횟수 감소가 함께 들어 있다. 합계는 벡터만 끄면 2.965 µs, 언롤도 끄면 7.984 µs가 되며, 후자는 Astra와 거의 같다. 최댓값은 벡터만 끄는 것으로 Astra 수준에 돌아간다.

### 상호 재귀

Astra는 `even_step -> odd_step -> even_step`을 각 함수 사이의 tail jump로 처리한다. 이때마다 함수 스택 프레임과 저장 레지스터를 복구하고 다시 설정한다.

Gemini는 작은 상호 재귀 함수의 본문을 IR에서 복제해 한 함수의 자기 반복문으로 합친다. 생성 어셈블리에서 더하기·XOR의 두 단계를 진행하고 같은 루프로 돌아가는 것을 확인했다. 이 문제에는 YMM 명령이 없다. 상호 재귀 인라이닝만 끄면 6.089 µs에서 14.213 µs로 느려져 Astra의 14.344 µs와 비슷해진다. 벡터화와 독립적인 구조 변환 효과다.

### 비꼬리 합계

입력은 `get(i) + sum(i + 1)` 형태다. Astra는 재귀 호출 뒤에 더하기가 남아 있어 매 원소마다 호출하며 부분값을 스택에 저장한다.

Gemini는 결합 가능한 연산을 인식해 누산기 인자를 추가한 함수를 만들고, 꼬리 재귀로 바꾼 뒤 루프와 벡터 경로를 생성한다. modulo 2^64 덧셈의 결합 법칙을 사용하는 변환이다.

SIMD와 언롤을 모두 끈 Gemini도 43.3 ns로 Astra의 92.3 ns보다 빠르다. 비꼬리 재귀 변환까지 끄면 76.3 ns가 된다. 그 뒤 언롤을 켜면 16.2 ns, 벡터 경로까지 켜면 6.8 ns다. 재귀 변환·언롤·벡터 경로 모두 기여한다.

### 보조 함수, 나눗셈과 피보나치

`helper_mix`에서는 두 코드 모두 작은 보조 함수를 인라이닝한다. 실제 Gemini의 도달 가능한 코드에는 YMM 명령이 없고 스칼라 4회 언롤 경로가 나온다. 벡터 경로 제거로 속도는 거의 바뀌지 않지만 언롤 제거로 12.6 µs에서 16.3 µs가 되어 Astra와 같아진다.

`divmod`는 배열 원소에 따라 분모가 바뀐다. Gemini의 벡터 표현식 판정은 나눗셈·나머지의 분모가 상수인 경우만 허용하므로 이 문제는 벡터화하지 않는다. 두 구현 모두 정수 `divq`를 사용하며 실행 시간도 거의 같다. 두 구현 모두 상수 분모에는 별도 최적화를 구현하지만 이 기본 문제의 주요 계산에는 적용되지 않는다.

피보나치도 SIMD를 사용하지 않는다. Gemini 원본은 한 재귀 분기를 누산기와 반복으로 바꾸고, Astra는 두 번 호출한다. 그러나 이번 작은 입력에서는 그 변환을 꺼도 Gemini의 실행 시간에 큰 차이가 없었다. SIMD 없는 일반 코드 생성에서도 Gemini는 중간 결과를 레지스터에 유지하는 반면 Astra는 재귀 호출 사이의 첫 결과를 스택에 저장한다. 어느 한 차이만을 주원인으로 정량화하지는 않았다. 둘 다 메모이제이션이나 동적 계획법으로 알고리즘을 바꾸지는 않는다.

## 별도로 발견한 정확성 오류

Gemini의 `simplify_expr()`는 두 상수의 이항 연산을 접을 때 먼저 `e->op = CB_CONST`로 바꾸고, 그 바뀐 `op`를 `eval_const_binop()`에 전달한다. 해당 함수에서 `CB_CONST`는 처리되지 않아 기본값 0이 반환된다.

재현 입력:

```text
(program (fn main () (add 2 3)))
```

참조 결과는 5인데 Gemini는 0을 반환한다. Astra는 5를 반환한다. 원본 코드를 고치지 않고 두 제출물에 같은 진단 문제를 넣어 확인했다. 원래 문제 8개는 이 오류를 검출하지 못했다. 따라서 이번 속도 수치는 원래 문제군에서의 결과이며 일반적인 AST 전체에 대한 정확성을 보증하지 않는다. 상수 표현식과 의미를 보존한 AST 변형을 추가한 평가가 필요하다.

### 이 오류가 성능 측정을 오염시켰는지 확인

현재 8개 문제의 측정에는 영향을 주지 않았다. Gemini 원본과 네 최적화 제거 변형에 대해 잘못된 폴딩 분기에 컴파일 시점 로그를 추가했으며, 모든 문제에서 해당 분기에 들어간 횟수가 0이었다.

별도의 분석용 복사본에서는 원래 연산으로 값을 계산한 뒤 `e->op`를 `CB_CONST`로 바꾸도록 두 문장의 순서만 수정했다. 수정 전후 생성 어셈블리를 비교한 결과 **5개 버전 × 8개 문제 = 40개 파일이 모두 바이트 단위로 동일**했다. 따라서 이 상수 폴딩 오류가 계산을 제거해 기존 성능 수치를 높인 것은 아니며, 앞의 벡터화·언롤·재귀 변환 비교에도 영향을 주지 않았다. 동일한 생성 코드이므로 이 확인을 위해 실행 시간을 다시 측정하지 않았다.

계측이 실제로 동작하는지도 `(add 2 3)` 진단으로 확인했다. 이 입력에서는 폴딩 로그가 발생했고, 오류를 수정한 복사본은 결과 5로 정확성 검사를 통과했다. `res/v1` 원본 소스는 수정하지 않았다.

```sh
python3 scripts/audit_v1_constant_folding.py
```

로그, 수정 전후 어셈블리와 확인 결과는 `build/analysis/v1/constant_fold_audit/summary.json` 및 같은 디렉터리의 하위 파일에 저장했다. 이 명령은 먼저 `scripts/analyze_v1.py`의 산출물이 있어야 한다.

## 재현과 산출물

```sh
make v1
python3 scripts/analyze_v1.py
```

`build/analysis/v1/summary.json`에 각 변형의 정확성·실행 시간·도달 가능한 어셈블리 통계·진단 결과를 저장했다. 각 하위 디렉터리에는 분석용 C 복사본, 컴파일 로그, 실행 파일, 생성된 문제별 어셈블리와 JSON 결과가 있다. `constant_fold_probe`에 오류 재현 입력과 두 제출물의 결과가 있다.
